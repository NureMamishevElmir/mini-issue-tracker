# Mini Issue Tracker — вимоги та контракт даних (ЛР1)

**Версія:** 1.3 (після трьох перехресних рев'ю, див. [review-log.md](review-log.md)) · **Тег:** `lab01-spec` · **Бригада:** Ус В., Козир Д., Мамішев Е., Дроздов А.

Цей документ — **єдине джерело істини** для моделі даних і бізнес-правил. [api-contract.md](api-contract.md),
[architecture.md](architecture.md) і майбутні тести посилаються на ідентифікатори звідси (FR, NFR, US/AC, D, BR, E)
і не переписують правила наново.

Вхідні дані: вихідний запит замовника, розділ 2 (FR-01–FR-08, межі обсягу) і розділ 3 (рішення замовника) завдання ЛР1.

**Позначки джерела:** `[З]` — рішення замовника з розділу 3 (заданий факт); `[D-xx]` — рішення команди, яке
формалізує прогалину (див. розділ 4.3); `[FR]` — функціональна вимога розділу 2.

---

## 1. Призначення та межі

Локальний REST-сервіс для невеликої команди, у якому учасник реєструє заявку про проблему програмного продукту,
а команда переглядає та фільтрує заявки, призначає виконавця, змінює пріоритет і статус та обговорює заявку в коментарях.

**Актори.** Два тестові користувачі з довідника: `1 — Agent A`, `2 — Agent B` [З]. Вони виступають виконавцями
заявок і авторами коментарів. Ідентифікатор, переданий у запиті, **не підтверджує** особу: автентифікації немає [З].

**Не входить до обсягу:** реєстрація, паролі, OAuth, рольова авторизація, email-сповіщення, вкладення, видалення
заявок, повнотекстовий пошук, пагінація, складний frontend, Docker, хмарне розгортання, векторна база, створення
користувачів через API, окремий список «важливих» заявок, історія змін, редагування й видалення коментарів.

## 2. Функціональні вимоги

| Код | Вимога | Межа реалізації |
|-----|--------|-----------------|
| FR-01 | Створення заявки | Назва (обов'язкова) і опис (необов'язковий); статус завжди `OPEN`; пріоритет `medium`, якщо не задано інший. |
| FR-02 | Перегляд та фільтрація | Список заявок і одна заявка за id; фільтри `status` і `priority` окремо та разом (логічне AND). |
| FR-03 | Редагування заявки | Часткове оновлення (PATCH) лише дозволених полів: `title`, `description`, `priority`, `assignee_id`. Статус змінюється окремою операцією. |
| FR-04 | Керування статусом | Лише переходи з матриці BR-01; помилка не змінює дані. |
| FR-05 | Призначення виконавця | Виконавець — один із двох користувачів довідника; `null` знімає призначення. |
| FR-06 | Коментарі | Додавання та перегляд коментарів до наявної заявки; автор — відомий користувач. |
| FR-07 | Збереження й валідація | SQLite; дані зберігаються після перезапуску; некоректні запити відхиляються без зміни даних. |
| FR-08 | Рекомендація AI (лише ЛР4) | Категорія, пріоритет і короткий підсумок; рекомендація **не змінює** заявку автоматично. У ЛР1 — лише майбутня історія US-08. |

| Код | Вимога | Спосіб перевірки |
|-----|--------|------------------|
| NFR-01 | **Відтворюваний локальний запуск.** Сервіс запускається з чистого клону за інструкцією README без ручного налаштування бази: створення venv, `pip install -r requirements.txt`, одна команда запуску. База створюється автоматично. | Учасник, який не писав код, на іншому комп'ютері клонує тег і виконує README; `GET /health` → `200` не пізніше ніж за 10 хв. Результат фіксується в звіті ЛР2. |

| NFR-04 | **Відсутність секретів у репозиторії.** Ключі API (для ЛР4) лише в `.env`, який є в `.gitignore`; у репозиторії тільки `.env.example` без значень. | `git grep -nE "sk-[A-Za-z0-9_-]{16,}" $(git rev-list --all)` не знаходить значень ключів у жодному коміті; `.env.example` містить лише назви змінних без значень; `git check-ignore .env` повертає збіг. |
| NFR-05 | **Робота без LLM.** FR-01–FR-07 працюють, коли LLM недоступна або ключ не задано; рекомендація (FR-08) тоді повертає помилку недоступності, а заявки не змінюються. | У ЛР3/ЛР4 увесь набір тестів FR-01–FR-07 проходить з порожнім `.env`; окремий тест: запит рекомендації без ключа не змінює заявку. |
| NFR-06 | **Атомарність змін.** Будь-яка відхилена операція (`4xx`) або внутрішня помилка не залишає часткових змін у базі. | Тести E-01, E-02 і E-03 перевіряють, що після відмови `GET` повертає попередній стан заявки повністю (усі поля), а кількість заявок і коментарів не змінилася. |

Дублікати об'єднано (у дужках — хто ще знайшов те саме).

| № | Хто | Неоднозначність у вихідному запиті | Ризик |

| N-02 | Ус В. (Дроздов А.) | Які є статуси і між якими дозволено переходити? Чи можна повернути закриту заявку? | Неконсистентний життєвий цикл, неперевірювані тести. |

| N-04 | Козир Д. | Які значення пріоритету і який типовий? | Невідомо, що зберігати при створенні. |

### 4.3. Рішення команди для справжніх прогалин

Кожне рішення не суперечить розділу 3 і не додає функціональності.

| ID | Прогалина | Рішення | Обґрунтування |
|----|-----------|---------|---------------|
| D-01 | Порядок перевірок, коли запит має кілька проблем | Спочатку форма запиту (`422`), потім існування заявки (`404`), потім стан (`409`). | Так поводиться FastAPI (тіло валідується до виклику обробника); один випадок → один код. |
| D-02 | PATCH з порожнім тілом `{}` | `422`, дані не змінюються. Перевіряється на рівні схеми запиту, тобто до перевірки існування заявки (D-01): `PATCH /issues/999 {}` → `422`. | Порожній запит — помилка клієнта; відрізняємо від «поле не передано» в непорожньому запиті. |
| D-03 | Невідомі або недозволені поля в тілі (у т. ч. `status`, `id`, `created_at`, `assignee_id` при створенні) | `422` для всього запиту. | Помилка клієнта не повинна мовчки ігноруватися; `status` змінюється лише окремою операцією [FR-03]. |
| D-04 | Чи є виконавець «основними даними», заблокованими після закриття | Так: на заявці `CLOSED` будь-яка зміна через `PATCH /issues/{id}`, включно з `assignee_id`, → `409`. | Розділ 3 забороняє редагувати закриту заявку; закрита заявка — кінцевий стан, перепризначення не має сенсу. |
| D-05 | `null` для полів, де він не означає «зняти значення» | І в `POST`, і в `PATCH`: `null` дозволено лише для `assignee_id` у PATCH (зняти призначення). `null` у `title`, `description`, `priority`, `author_id`, `text` → `422`. | Відрізняє «не передано» (не змінювати) від «передано null». |
| D-06 | Нормалізація опису | Опис зберігається як є (без обрізання); `null` → `422`. | Розділ 3 описує обрізання лише для назви. |
| D-07 | Чи задається виконавець при створенні | Ні: `POST /issues` приймає лише `title`, `description`, `priority`; виконавець після створення — `null`. | FR-01 перелічує лише назву, опис і пріоритет; призначення — окрема дія FR-05. |
| D-08 | Коментар лише з пробілів | Текст обрізається з обох боків; після обрізання 1–1000 символів, інакше `422`. Зберігається обрізаний текст. | «Непорожній текст» — пробіли змісту не несуть. |
| D-09 | Формат часу | ISO 8601 в UTC з суфіксом `Z`, точність до секунд: `2026-11-10T09:15:30Z`. | Однозначно для клієнта й тестів. |
| D-10 | Ключ сортування «за порядком створення» | За `id` зростанням (id монотонно зростає з часом створення). | `created_at` має точність до секунд і може збігатися. |
| D-11 | Як рахувати довжину рядків | У кодових точках Unicode (`len()` у Python), без NFC/NFD-нормалізації; для назви й тексту коментаря — після обрізання крайніх пробільних символів Unicode (як `str.strip()`: пробіл, `\t`, `\n`, NBSP тощо). | Українські літери рахуються як один символ; правило однозначно перевіряється тестом. |
| D-12 | Окремий маршрут «важливих» заявок | Не створюємо; використовуються фільтри FR-02. | Зайва функція поза FR. |
| D-13 | Невідомі параметри запиту (`?foo=1`, `?Status=OPEN`) | `422`, як і невідомі поля тіла. Повторений параметр (`?status=OPEN&status=CLOSED`) і порожнє значення (`?status=`) — теж `422`. | Узгоджено з D-03: помилка клієнта не ігнорується мовчки. |
| D-14 | Приведення типів (`"assignee_id": "2"`, `"author_id": true`, `"title": 123`) | Строгі типи: значення іншого JSON-типу → `422`, без автоматичного перетворення. | Однакова поведінка для всіх клієнтів. У Pydantic — `strict=True` разом із `Literal[...]` для переліків, а не `Enum`: у строгому режимі рядок `"high"` не приймається як значення `Enum`. |
| D-15 | `{id}` у шляху ≤ 0 (`/issues/0`) | `422`, а не `404`. | Такий id не може існувати за форматом (додатне ціле, розділ 6), тому це помилка форми запиту, а не «заявки немає». |
| D-16 | Додаткові поля, яких немає в розділі 3 (наприклад, `updated_at`) | Не додаємо. | Розділ 3 перелічує всі дані заявки; поле не потрібне жодній FR (відхилена пропозиція AI, AI-02). |

## 5. User stories і критерії приймання

Роль «учасник команди» — будь-який із двох тестових користувачів. Критерії описують спостережувану поведінку API.

### US-01 — Створення заявки · FR-01, FR-07
Як учасник команди, я хочу створити заявку з назвою й описом, щоб проблему було зафіксовано і її можна було відстежувати.

- **AC-01-01 (позитивний).** Given заявок немає, When надходить `POST /issues` з `{"title": "  Login fails  ", "description": "Crash after login"}`, Then відповідь `201`, у тілі `title = "Login fails"`, `status = "OPEN"`, `priority = "medium"`, `assignee_id = null`, присвоєно `id` і `created_at`.
- **AC-01-02 (граничний).** Given порожня база, When надходять створення з назвою `"ab"` (2 символи), `"abc"` (3), 120 і 121 символ, Then для 3 і 120 — `201`, для 2 і 121 — `422`, і в списку лише дві нові заявки. Назва `"   ab   "` → `422` (після обрізання 2 символи).
- **AC-01-03 (негативний).** When створення з `"priority": "High"` або з полем `"status": "CLOSED"`, Then `422`, заявку не створено.
- **AC-01-04 (граничний).** Given порожня база, When надходять створення з описом із 2000 символів, із 2001 символу і без поля `description`, Then відповідно `201`, `422` і `201` з `description = ""`.
- **AC-01-05 (граничний, D-11).** Given порожня база, When надходять створення з назвою `"Баг"` (3 кириличні символи) і з назвою з 121 кириличної літери, Then відповідно `201` і `422`.

### US-02 — Перегляд і фільтрація · FR-02
Як учасник команди, я хочу переглядати заявки й фільтрувати їх за статусом і пріоритетом, щоб швидко знаходити потрібні, зокрема важливі відкриті.

- **AC-02-01 (позитивний).** Given заявки з id 1, 2, 3, When `GET /issues`, Then `200` і масив у порядку `1, 2, 3`.
- **AC-02-02 (позитивний).** Given `#1 OPEN/high`, `#2 OPEN/low`, `#3 CLOSED/high`, When `GET /issues?status=OPEN&priority=high`, Then повертається лише `#1`.
- **AC-02-03 (граничний).** When фільтр не знаходить жодної заявки, Then `200` і `[]`.
- **AC-02-04 (негативний).** When `GET /issues/999` для неіснуючої заявки, Then `404`.
- **AC-02-05 (негативний).** When `GET /issues?status=open` (неправильний регістр), Then `422`.
- **AC-02-06 (позитивний, окремі фільтри).** Given `#1 OPEN/high`, `#2 OPEN/low`, `#3 CLOSED/high`, When `GET /issues?status=OPEN`, Then повертаються `#1, #2`; When `GET /issues?priority=high`, Then повертаються `#1, #3`.
- **AC-02-07 (негативний, D-13, D-15).** When `GET /issues?foo=1`, `GET /issues?status=OPEN&status=CLOSED`, `GET /issues?status=` або `GET /issues/0`, Then `422`.

### US-03 — Часткове редагування · FR-03, FR-07
Як учасник команди, я хочу змінити лише потрібні поля заявки, щоб уточнити її, не зачіпаючи решту даних.

- **AC-03-01 (позитивний).** Given заявка `{title: "Login fails", priority: "medium"}`, When `PATCH /issues/1` з `{"priority": "high"}`, Then `200`, `priority = "high"`, а `title`, `description`, `assignee_id`, `status` не змінилися.
- **AC-03-02 (атомарність).** When `PATCH` з `{"title": "Valid new title", "priority": "urgent"}`, Then `422`, і `GET /issues/1` повертає попередню назву та пріоритет.
- **AC-03-03 (негативний).** When `PATCH` з `{}` або з `{"status": "CLOSED"}`, Then `422`, дані без змін.
- **AC-03-04 (негативний).** Given заявка `CLOSED`, When `PATCH` з `{"title": "New title"}`, Then `409`, дані без змін.
- **AC-03-05 (порядок перевірок, D-01, D-02).** Given заявки 999 немає, When `PATCH /issues/999` з `{}`, Then `422`; When `PATCH /issues/999` з `{"priority": "high"}`, Then `404`.
- **AC-03-06 (граничний, BR-03).** Given заявка `CLOSED` з `priority = "medium"`, When `PATCH` з `{"priority": "medium"}` (те саме значення), Then `409`.

### US-04 — Зміна статусу · FR-04
Як учасник команди, я хочу змінювати статус заявки, щоб відображати поточний стан роботи над нею.

- **AC-04-01 (позитивний).** Given заявка `OPEN`, When `PATCH /issues/1/status` з `{"status": "IN_PROGRESS"}`, Then `200` і `status = "IN_PROGRESS"`.
- **AC-04-02 (негативний).** Given заявка `CLOSED`, When надходить зміна на `OPEN`, Then `409` і збережений статус залишається `CLOSED`.
- **AC-04-03 (граничний).** Given заявка `IN_PROGRESS`, When зміна на `IN_PROGRESS`, Then `200`, заявка без змін.
- **AC-04-04 (негативний).** When `{"status": "RESOLVED"}` або `{"status": "open"}`, Then `422`.
- **AC-04-05 (повнота матриці).** Given заявка в кожному з трьох статусів, When запитується кожен із трьох статусів (9 комбінацій), Then код відповіді та збережений статус відповідають таблиці BR-01.
- **AC-04-06 (негативний).** Given заявки 999 немає, When `PATCH /issues/999/status` з `{"status": "CLOSED"}`, Then `404`.

### US-05 — Призначення виконавця · FR-05
Як учасник команди, я хочу призначити заявці виконавця або зняти призначення, щоб було зрозуміло, хто за неї відповідає.

- **AC-05-01 (позитивний).** When `GET /users`, Then `200` і рівно два користувачі: `1 Agent A`, `2 Agent B`.
- **AC-05-02 (позитивний).** Given заявка без виконавця, When `PATCH /issues/1` з `{"assignee_id": 2}`, Then `200`, `assignee_id = 2`; потім `{"assignee_id": null}` → `assignee_id = null`.
- **AC-05-03 (негативний).** Given заявка з `assignee_id = 1`, When `PATCH` з `{"assignee_id": 3}` або `{"assignee_id": 0}`, Then `422` і `assignee_id` залишається `1`.
- **AC-05-04 (негативний, D-14).** Given заявка без виконавця, When `PATCH` з `{"assignee_id": "2"}` (рядок замість числа), Then `422` і `assignee_id` залишається `null`.

### US-06 — Коментарі · FR-06
Як учасник команди, я хочу додавати й переглядати коментарі до заявки, щоб обговорювати проблему в її контексті.

- **AC-06-01 (позитивний).** When `POST /issues/1/comments` з `{"author_id": 1, "text": "Reproduced on Chrome"}`, Then `201`, у тілі `issue_id = 1`, `author_id = 1`, `created_at`; коментар з'являється в `GET /issues/1/comments` останнім.
- **AC-06-02 (граничний).** Given заявка 1 існує, When додаються коментарі з текстом `"   "`, із 1000 і з 1001 символу, Then відповідно `422`, `201`, `422`.
- **AC-06-03 (негативний).** Given заявка 1 існує, а 999 — ні, When `POST /issues/1/comments` з `author_id = 5`, Then `422`; When `POST` або `GET` коментарів заявки 999, Then `404`.
- **AC-06-04 (граничний).** Given заявка `CLOSED`, When додається коментар, Then `201`.

### US-07 — Збереження даних · FR-07
Як учасник команди, я хочу, щоб заявки й коментарі зберігалися між запусками, а помилкові запити не псували дані.

- **AC-07-01 (позитивний).** Given створено заявку з коментарем, When сервіс зупинено й запущено знову з тією самою базою, Then `GET /issues/1` і `GET /issues/1/comments` повертають ті самі дані.
- **AC-07-02 (негативний).** Given 3 заявки, When надходить `POST /issues` з `{"title": "ab"}`, Then `422` і `GET /issues` повертає ті самі 3 заявки.

### US-08 — Рекомендація AI (майбутня, ЛР4) · FR-08
Як учасник команди, я хочу отримати рекомендовані категорію, пріоритет і короткий підсумок заявки, щоб швидше її класифікувати.

## 7. Бізнес-правила

### BR-01. Матриця переходів статусу (`PATCH /issues/{id}/status`)

Рядок — поточний статус, стовпець — запитаний.

| Поточний \ Запитаний | `OPEN` | `IN_PROGRESS` | `CLOSED` |
|----------------------|--------|---------------|----------|
| `OPEN` | без змін, `200` | дозволено, `200` | дозволено, `200` |
| `IN_PROGRESS` | заборонено, `409` | без змін, `200` | дозволено, `200` |
| `CLOSED` | заборонено, `409` | заборонено, `409` | без змін, `200` |

Дозволено 3 переходи, 3 комбінації — повтор поточного статусу (успіх без змін), 3 — заборонені повернення.
`CLOSED → CLOSED` дає `200`, бо повтор поточного статусу не є помилкою [З]; змінити статус закритої заявки неможливо.
Значення поза переліком → `422` (E-01).

### BR-02. Операції із закритою заявкою

| Операція | `OPEN` / `IN_PROGRESS` | `CLOSED` |
|----------|------------------------|----------|
| Перегляд (`GET /issues`, `GET /issues/{id}`) | так | так |
| Редагування `title`, `description`, `priority`, `assignee_id` | так | ні → `409` [З, D-04] |
| Зміна статусу | за BR-01 | ні → `409`; той самий статус → `200` |
| Додавання та перегляд коментарів | так | так [З] |

### BR-03. Часткове оновлення (`PATCH /issues/{id}`)

Тіло — JSON-об'єкт; змінюються лише передані поля, решта залишається без змін [З].

| Випадок | Поведінка |
|---------|-----------|
| Поле не передано | Значення не змінюється. |
| `{"assignee_id": null}` | Знімає призначення. |
| `null` для `title`, `description`, `priority` | `422` [D-05]. |
| Порожнє тіло `{}` | `422` [D-02]. |
| Невідоме або недозволене поле (`status`, `id`, `created_at`, `foo`) | `422` для всього запиту [D-03]. |
| Коректні й некоректні поля разом | `422`, **жодна** зміна не зберігається [З]. |
| Заявка не `CLOSED`, значення збігаються з поточними | `200`, фактичних змін немає. |
| Заявка `CLOSED` і непорожнє коректне тіло (навіть якщо значення не змінюються) | `409` [BR-02, D-04]. Має пріоритет над попереднім рядком. |

**Атомарність (NFR-06).** Схема запиту (шар API) перевіряє всі поля (`422`), сервіс — існування заявки й стан (`404`,
`409`), потім застосовує поля однією транзакцією разом із цими перевірками. Помилка на
будь-якому кроці — відкат усієї транзакції.

### BR-04. Порядок і зв'язки

Списки заявок і коментарів упорядковано за зростанням `id` [З, D-10]. Фільтри `status` і `priority` необов'язкові;
разом діють як AND [FR-02]; порожній результат — `200` з `[]` [З].

### Каталог результатів і помилок

Порядок перевірки: E-01 → E-02 → E-03 [D-01].

| ID | Ситуація | Результат | Приклади |
|----|----------|-----------|----------|
| S-01 | Успішне створення | `201`, створений об'єкт | заявка, коментар |
| S-02 | Успішне читання або зміна | `200`, актуальний об'єкт або масив | GET, PATCH, повтор статусу |
| S-03 | Фільтр нічого не знайшов | `200`, `[]` | `?status=CLOSED`, коли закритих немає |
| E-01 | Некоректні вхідні дані | `422`, дані без змін | відсутнє обов'язкове поле, довжина, тип (D-14), невідоме поле або параметр запиту (D-03, D-13), `null` (D-05), невідомий користувач, значення поза enum, порожній PATCH, неправильні фільтри, нечислове або ≤ 0 `id` у шляху |
| E-02 | Заявки не існує | `404`, дані без змін | будь-який маршрут з `{id}` неіснуючої заявки (маршрути 5–9) |
| E-03 | Операція суперечить стану | `409`, дані без змін | заборонений перехід (BR-01), редагування `CLOSED` (BR-02) |
